# Технический дизайн ОВДП Трекера

Документ описывает текущую реализацию приложения и технические контракты, перенесённые из README.
Пользовательские сценарии и запуск находятся в [руководстве пользователя](../readme.md).
План развития и проектные решения MVP находятся в
[OpenSpec design](../openspec/changes/initial-bond-portfolio-mvp/design.md),
а требования — в [спецификациях изменения](../openspec/changes/initial-bond-portfolio-mvp/specs).
Результаты сквозной и браузерной проверки MVP приведены в [отчёте проверки](mvp-verification.md).

## Архитектура и границы модулей

Приложение рассчитано на одного пользователя на одном компьютере.
Flask формирует HTML через Jinja, данные хранятся в SQLite.
JavaScript обслуживает загрузку ISIN, редактор календаря, переключение валюты и защиту незавершённых форм.
Проверка и сохранение предметных данных выполняются на сервере.

| Модуль | Ответственность |
| --- | --- |
| `ovdp_tracker/__init__.py` | Фабрика приложения, конфигурация, проверка хранилища и регистрация маршрутов. |
| `ovdp_tracker/__main__.py` | Локальный запуск через `python -m ovdp_tracker`. |
| `ovdp_tracker/web.py` | HTTP, подготовка значений формы, ответы поиска ISIN и передача `Database`. |
| `ovdp_tracker/db.py` | SQL, схема, соединения, транзакции и высокоуровневое хранение данных. |
| `ovdp_tracker/purchases.py` | Проверка выпуска, календаря и покупки, сравнение общих полей, создание покупки. |
| `ovdp_tracker/portfolio.py` | Остатки, группировка покупок в позиции ISIN и причитающиеся выплаты. |
| `ovdp_tracker/payments.py` | Подтверждение фактических выплат с проверкой прав, дат, сумм и истории покупки. |
| `ovdp_tracker/money.py` | Точный разбор денежных строк и расчёт сумм операций. |
| `ovdp_tracker/nbu.py` | Получение справочника НБУ и разбор записи выпуска. |

Внешних шрифтов, CDN, библиотек оформления и сборки frontend нет.
Шаблоны и ресурсы входят в пакет. Просмотр сохранённых данных и ручной ввод не требуют сети.
Обращение к НБУ выполняется только при автоматической загрузке реквизитов.

Локальный сервер слушает `127.0.0.1:5000`. Debug, интерактивный отладчик, reloader
и загрузка dotenv отключены в точке входа, в том числе при заданном `FLASK_DEBUG`.
Приложение не проектируется для многопользовательского или публичного сетевого развёртывания.

## Хранение и совместимость

Путь по умолчанию — `instance/portfolio.sqlite3` относительно корня проекта, независимо от рабочего каталога запуска.
Для тестов или другого хранилища фабрика `create_app(config)` принимает путь через настройку `DATABASE`.
Первый запуск создаёт пустую базу без демонстрационных операций; повторный запуск сохраняет данные.
Весь каталог `instance/` и отдельные файлы SQLite исключены из Git.

Текущая версия схемы — **3**. Основные сущности:

- `banks` — названия банков с уникальным нормализованным именем.
- `bond_issues` — общие реквизиты выпуска, уникальный ISIN и справочные метаданные НБУ.
- `bond_lots` — отдельные покупки с датой, ценой, количеством, ссылками на выпуск и банк.
- `scheduled_payments` — общий календарь выпуска с собственной суммой каждой выплаты на одну бумагу.
- `actual_payments` — подтверждения выплат для конкретных покупок.
- `sales` — продажи из конкретных покупок.

У выпуска нет общего поля суммы купона. Даты до покупки сохраняются в полном календаре.
Купон и погашение в один день — разные события. У выпуска допускается одно погашение;
уникальный индекс запрещает второе даже с другой датой.

Составные внешние ключи не позволяют подтвердить для покупки событие другого выпуска.
Пара покупки и планового события уникальна. Удаление покупки очищает только её продажи
и фактические выплаты, сохраняя выпуск, календарь и банк.
Общее событие с подтверждением не удаляется каскадно вместе с фактом.

### Несовместимые базы

Схема 3 несовместима с версиями 1/2. Миграция и перенос старой истории не реализованы.
Неизвестная версия или существующая схема без версии вызывает `SchemaVersionError`;
файл при этом не удаляется и не перезаписывается. Обычный запуск данные не сбрасывает.

Для пересоздания ненужной базы разработки остановите приложение и сохраните резервную копию,
если данные могут понадобиться. Затем из корня проекта выполните:

```powershell
Remove-Item -LiteralPath .\instance\portfolio.sqlite3
python -m ovdp_tracker
```

Удаление файла безвозвратно удаляет содержащиеся в нём данные; новый запуск создаёт пустую схему 3.

## API хранилища и транзакции

Все SQL, настройка хранилища и соединения сосредоточены в `db.py`.
`Database` не зависит от Flask, `g`, `current_app` и контекста приложения.
Внешний API возвращает обычные словари и списки, не передаёт соединения, курсоры и `sqlite3.Row`.

| Данные | Методы `Database` |
| --- | --- |
| Банки | `add_bank`, `get_bank`, `list_banks`, `delete_bank` |
| Выпуски | `add_issue`, `get_issue`, `get_issue_by_isin`, `list_issues` |
| Покупки | `add_lot`, `get_lot`, `list_lots`, `delete_lot` |
| Плановые выплаты | `add_scheduled_payment`, `list_scheduled_payments` |
| Фактические выплаты | `add_actual_payment`, `list_actual_payments` |
| Продажи | `add_sale`, `list_sales` |

Методы получения отдельной записи возвращают `None`, если она не найдена;
методы удаления возвращают признак удаления. `get_schema_version()` возвращает номер схемы.
`get_lot` и `list_lots` дополняют покупку общими реквизитами выпуска при чтении.
В таблице покупок эти реквизиты не дублируются.

`add_issue` принимает ISIN, валюту, номинал, погашение и справочные метаданные.
`add_lot` получает `issue_id`, дату и цену покупки, количество и `bank_id`.
`add_scheduled_payment` получает `issue_id`, тип, дату и сумму `amount` на одну бумагу.
Плановые события выбираются по `issue_id`, факты и продажи — по `lot_id`.
`add_actual_payment` требует `lot_id`, `scheduled_payment_id`, фактическую дату и общую сумму.
`add_bank` обрезает крайние пробелы и повторно использует название без учёта регистра,
сохраняя первоначальное написание.

Одиночные записи сохраняются автоматически. Связанные изменения выполняются через
`with database.transaction():`; исключение откатывает всю группу. Контекст не выдаёт соединение.

```python
from ovdp_tracker.db import Database

with Database("instance/portfolio.sqlite3") as database:
    with database.transaction():
        bank = database.add_bank("Банк А")
```

Выход из внешнего контекста закрывает соединение. `close()` допускает повторный вызов;
обращение к закрытому экземпляру вызывает `DatabaseError`.
Ограничения хранения выражаются через `DataIntegrityError`, прочие ошибки SQLite — через `DatabaseError`.
Внешние модули обрабатывают исключения `db`, а не `sqlite3`.
Хранилище обеспечивает ограничения схемы и формат денежных значений;
финансовые расчёты и полная проверка согласованности истории относятся к предметным модулям.

HTTP-обработчики получают `Database` явно через `@with_database` из `web.py`.
Обёртка создаёт отдельный экземпляр на запрос, передаёт его первым аргументом обработчику
и закрывает после успеха или исключения. Соединение не разделяется между запросами.
При старте отдельный краткоживущий экземпляр проверяет или создаёт схему.

## HTTP и сохранение покупки

| Метод и путь | Назначение |
| --- | --- |
| `GET /` | Действующие позиции; `currency` принимает UAH, USD, EUR, по умолчанию UAH. |
| `GET /history` | Полностью закрытые позиции с тем же фильтром валюты. |
| `GET /issues/<isin>` | Реквизиты выпуска, календарь и все покупки; 404 при отсутствии позиции. |
| `GET /purchases/<int:lot_id>` | Карточка покупки; 404 при неизвестном идентификаторе. |
| `GET /purchases/new` | Новая форма с текущей локальной датой покупки. |
| `POST /purchases/new` | Проверка и сохранение покупки с перенаправлением в портфель её валюты. |
| `GET /issues/lookup?isin=…` | Загрузка нового выпуска из НБУ или получение сохранённых общих полей. |

Неподдерживаемая валюта портфеля вызывает HTTP 400.
Поиск с `source=local` использует только сохранённые данные, без запроса НБУ.
Ответ поиска содержит `values`, `existing` и, при необходимости, `warning` и `details_url`.
Для нового импортированного выпуска выдаётся подписанный `issue_token`; ошибка возвращается в поле `error`.
Отсутствующий в НБУ ISIN даёт 404, ошибки загрузки или неподдерживаемые данные нового выпуска — 502.

Форма сохраняет выпуск, полный календарь, банк и покупку одной транзакцией.
При успехе происходит redirect на главную с `saved=1` и валютой выпуска.
Ошибки проверки возвращают заполненную форму с HTTP 400; ошибки хранения — с HTTP 503.
Частичных записей и новых банков после неудачной попытки не остаётся.

Подписанный снимок НБУ проверяется при сохранении, чтобы восстановить недоступные для редактирования поля
без повторного запроса. Подпись и принадлежность снимка ISIN проверяются на сервере.
Если `SECRET_KEY` не задан, ключ создаётся при запуске приложения.

Известный ISIN использует сохранённые общие поля. Ответ НБУ их не обновляет;
расхождение показывается предупреждением. Подмена валюты, номинала, метаданных, даты или суммы события
при повторной покупке отклоняется до записи покупки и банка, независимо от режима ввода.
`issue_signature()` сравнивает общие поля и полный календарь по значениям, включая точные денежные суммы.

## Интеграция с НБУ

Источник — `https://bank.gov.ua/depo_securities?json`.
`NbuClient` использует стандартную библиотеку, тайм-аут 10 секунд и ограничение ответа 4 МиБ.
Каждый поиск выполняет новый запрос без кеширования. JSON-числа с дробной частью читаются через `Decimal`.
ISIN нормализуется и проверяется как 12-символьный идентификатор;
выбирается точное совпадение `cpcode` с категорией `cptype == "DCP"`.
Отсутствующая или неоднозначная запись отклоняется.

`parse_bond_data(record)` разбирает одну запись в `{"issue": metadata, "payments": events}`.

| Поле НБУ | Поле приложения |
| --- | --- |
| `cpcode` | `isin` |
| `val_code` | `currency` |
| `nominal` | `nominal` |
| `razm_date` | `issue_date` |
| `pgs_date` | `maturity_date` |
| `auk_proc` | `nominal_rate` |
| `pay_period` | `coupon_period` |
| `cpdescr` | `bond_type` |

Каждый элемент `payments` преобразуется отдельно: `pay_date` → `planned_date`, `pay_val` → `amount`.
Тип `pay_type == "1"` означает купон, `"2"` и `"3"` — обычное и досрочное погашение.
Неизвестные типы сохраняются при разборе для последующей проверки поддерживаемого календаря.
Разбор не обращается к сети, не пишет в базу и не требует параметров покупки.

`validate_imported_issue()` отдельно проверяет валюту, денежную точность, даты и поддерживаемость календаря.
Неполный ответ и график с несколькими погашениями не импортируются частично.
Поддерживаются UAH, USD и EUR, один обычный или досрочный платёж погашения.
Купоны берутся из исходных дат и сумм: ставка и период не используются для генерации календаря.
Номинальная ставка справочная, доходность покупки из неё не вычисляется.

При отказе НБУ известный ISIN остаётся доступен по сохранённым реквизитам.
Новый выпуск требует повторной загрузки или ручного ввода.
При смене ISIN или режима интерфейс отменяет предыдущую загрузку;
запоздалый ответ не должен заполнять другую бумагу или заменять ручной черновик.

## Денежные значения и расчёты портфеля

`parse_money` принимает денежную строку и возвращает `Decimal`, без промежуточного `float`.
Допустимы точка или запятая, знак и крайние пробелы.
Разделители тысяч, экспоненциальная запись, нечисловые и бесконечные значения,
числовые объекты вместо строк и более двух дробных знаков вызывают `ValueError`.
Автоматического округления нет: `1000,01` допустимо, `1000,005` и `1000,010` — ошибка.

Хранилище записывает номинал, цены и суммы как точные десятичные строки в полях `TEXT`.
`operation_amount(unit_amount, quantity=1)` умножает `Decimal` на целое неотрицательное количество
и возвращает точную сумму с двумя дробными знаками. Агрегаты суммируют суммы операций.
Например, `operation_amount(parse_money("1000,01"), 3)` даёт `Decimal("3000.03")`.
Положительность цены и количества проверяется на уровне предметной операции;
денежные функции допускают ноль и отрицательные денежные потоки.

`portfolio.py` группирует покупки по выпуску. Остаток учитывает продажи и фактическое погашение
до текущей локальной даты включительно. Позиция закрыта, только когда закрыты все её покупки.
Прошедшая плановая дата сама по себе не подтверждает выплату и не обнуляет остаток.

План покупок сохраняет общий календарь, но исключает события до даты покупки.
Продажи уменьшают количество участвующих в последующих выплатах бумаг.
В один день применяется порядок «покупка → купон → продажи → погашение».
Подтверждения независимы для каждой покупки и не меняют общий календарь.
Фактическое погашение прекращает ожидания более поздних купонов этой покупки,
сохраняя купон дня погашения и уже записанные факты.

В портфеле ближайший купон выбирается от текущей даты включительно среди положительных
неподтверждённых выплат действующих покупок. Полностью подтверждённые и нулевые купоны пропускаются.
Общее число купонов в деталях включает весь календарь, в том числе прошлые и нулевые купоны,
без погашения. В колонке доходности показывается только сохранённая номинальная ставка.
Прибыль и доходность конкретной покупки пока не реализованы.

## Подтверждение выплат

`payments.confirm_payment(database, lot_id, event_id, values, today)` записывает фактические дату и общую сумму
для пары «покупка + событие». В одной транзакции он получает актуальные права через `get_lot_details`,
проверяет положительную сумму и дату от покупки до текущего локального дня и сохраняет факт через
`Database.add_actual_payment`. Проверка `check_history` после вставки откатывает транзакцию, если фактическое
погашение делает сохранённую продажу недопустимой. SQL и схема остаются в `db.py`; версия схемы не меняется.

Повторный вызов для подтверждённой пары возвращает первоначальный факт без перезаписи даты или суммы.
Нулевые купоны и события без прав отклоняются. Прошлый причитающийся купон закрытой покупки доступен
для подтверждения независимо от текущего остатка. План общего выпуска и факты других покупок сохраняются.

Маршрут `GET/POST /purchases/<lot_id>/payments/<event_id>/confirm` использует `@with_database` и общий шаблон
`payment_form.html` с защитой несохранённого ввода. При ошибке сохраняются исходные строки и baseline;
после успеха открывается карточка покупки. Ссылки доступны в выплатах покупки и её пункте календаря ISIN.

## Редактор календаря и защита форм

`_coupon_editor.html` и `coupon-calendar.js` реализуют строки из даты и суммы на одну облигацию.
Добавление, удаление и сортировка сохраняют пары, включая незавершённые строки при ошибке отправки.
`initializeCouponEditors()` вызывается после восстановления черновика до подключения защиты ухода.
Компоненты обмениваются массивом `coupons` вида `[{"date": "2027-06-01", "amount": "85,50"}]`.
Отдельной копии `_coupon_rows` нет. Только на границе HTML-формы массив кодируется в JSON;
обработчик декодирует его до предметной проверки. Суммы остаются строками до разбора в `Decimal`.

В новом ручном выпуске форма выводит погашение из максимальной купонной даты,
а при пустом календаре требует отдельную дату погашения. Сумма погашения равна номиналу.
Купоны могут различаться по сумме, быть нулевыми и предшествовать покупке;
повторные даты и отрицательные суммы отклоняются. Календарь НБУ и известного ISIN недоступен для правки.
Ручной черновик хранится отдельно от загруженных данных при переключении режима.

`unsaved-form.js` из базового шаблона сравнивает текущие значения с исходным снимком.
Форма подключается атрибутом `data-unsaved-form`, при ошибке задаёт `data-unsaved-error="true"`
и включает `unsaved_baseline.html`. Снимок переносится через отклонённые отправки.
В сравнение входят именованные поля, отключённые поля и динамические строки.
Служебные элементы исключаются через `data-unsaved-ignore`, загруженный снимок включается
через `data-unsaved-value="source"`. Снимок не используется для проверки предметных данных.

Внутренние ссылки и отмена открывают диалог «Остаться / Выйти без сохранения».
Подтверждённый уход не пишет данные и не вызывает второе предупреждение.
Неизменённая форма и возврат к исходным значениям не требуют подтверждения.
Отправка формы подавляет предупреждение; ошибка сохраняет введённые данные и защиту ухода.

Для reload, закрытия и истории браузера используется `beforeunload`.
Его текст и доступность определяет браузер; предупреждение обычно требует взаимодействия со страницей
и не гарантируется при аварийном завершении или закрытии мобильного приложения.
Защита требует JavaScript и не восстанавливает черновик после закрытия страницы.

## Шаблоны, навигация и визуальные проверки

`base.html` задаёт верхние разделы и хлебные крошки; оформление находится в `static/style.css`.
Портфель остаётся активным на карточках и форме; «Выплаты» и «Статистика» открывают самостоятельные разделы.
Путь карточки — «Портфель / ISIN / Покупка №…» независимо от referrer и способа открытия.
Действующие и закрытые позиции сохраняют фильтр валюты.

На узком экране поля перестраиваются в столбец, кнопки и навигация переносятся,
широкие таблицы прокручиваются внутри своего блока. Для таблиц предусмотрен фокус через Tab,
для ссылок, полей и кнопок — видимая рамка фокуса.
При изменениях интерфейса проверяются портфель, детали выпуска, карточка покупки и оба режима формы
на обычной ширине и при 320–390 px: прокрутка, доступность кнопок, пустые списки, ошибки и успешная запись.

## Проверки и разработка

Зависимости разработки и тестирования зафиксированы в `requirements-dev.txt`,
который включает зависимости приложения из `requirements.txt`.

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest
```

Конфигурация — `pytest.ini`; тесты находятся в `tests/`.
Для подробного вывода используется `-v`, для отдельного файла — например, `python -m pytest tests/test_db.py`.
Новые тесты пишутся функциями с обычными `assert`, фикстурами и параметризацией pytest.
Тестовые SQLite-файлы создаются через `tmp_path`; рабочая база из `instance/` не используется.

| Тесты | Область проверки |
| --- | --- |
| `test_db.py` | Публичный API, общий календарь, независимые факты, атомарность и перезапуск. |
| `test_db_storage.py` | Схема, закрытие соединений, составные ключи и сохранность несовместимых файлов. |
| `test_web.py` | Передача и закрытие экземпляров `Database` в HTTP. |
| `test_money.py` | Формат денежных строк, точность и суммы операций. |
| `test_purchases.py` | Форма покупки, значения по умолчанию, проверки и откат при сбоях. |
| `test_portfolio.py` | Позиции, остатки, выплаты, независимость покупок и перезапуск. |
| `test_confirm_payment.py` | Подтверждение, права на выплаты, повторы, погашение, откат и защита формы. |
| `test_nbu.py` | Контракт НБУ, ошибки, каждый новый запрос и автозагрузка без реальной сети. |
| `test_coupon_editor.py` | Пары дат и сумм, сортировка, погашение и восстановление незавершённого ввода. |
| `test_unsaved_forms.py` | Защита ухода и отсутствие записи черновиков при отмене. |
| `test_navigation.py` | Общая навигация, хлебные крошки и переходы между страницами. |
| `test_end_to_end.py` | Полный цикл двух покупок: НБУ, выплаты, продажа, правки, расчёты, перезапуск и удаление. |

Прямое обращение к SQLite допускается только в низкоуровневых тестах хранилища.
Workflow `.github/workflows/tests.yml` запускает полный pytest на Python 3.11 в Ubuntu и Windows
при push, pull request и ручном запуске. До коммита следует проверять `git diff --check`.

Правила работы находятся в [AGENTS.md](../AGENTS.md), контекст OpenSpec — в
[openspec/config.yaml](../openspec/config.yaml).
