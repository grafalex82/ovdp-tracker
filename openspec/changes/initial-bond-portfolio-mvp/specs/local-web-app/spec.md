# Локальное веб-приложение

## Purpose

Предоставляет одному пользователю браузерный интерфейс для ручного учёта ОВДП и надёжно сохраняет введённую историю на локальном компьютере между запусками.

## ADDED Requirements

### Requirement: Локальный запуск без отдельной инфраструктуры
Приложение MUST запускаться одной документированной командой Python после установки зависимостей и быть доступным в браузере только через loopback-интерфейс по умолчанию. Авторизация, Docker, virtualenv, внешняя СУБД и внешние API MUST не требоваться для работы MVP.

#### Scenario: Работа без сети
- **WHEN** зависимости установлены и пользователь запускает приложение на компьютере без доступа в интернет
- **THEN** формы, портфель, история и расчёты работают локально без страницы входа и сетевых запросов к сторонним сервисам

### Requirement: Основные страницы
Приложение MUST предоставлять портфель действующих пакетов на главной странице, форму покупки, карточку пакета с выплатами и продажами, доступ к закрытой истории и страницу статистики с месячной таблицей. Пользователь MUST иметь возможность переходить между ними через общую навигацию. Графики MUST отсутствовать в MVP.

#### Scenario: Работа с пакетом из портфеля
- **WHEN** пользователь открывает пакет в портфеле
- **THEN** он видит параметры покупки, историю продаж, ожидаемые и полученные выплаты, прибыль, XIRR и простую годовую доходность, а также доступные действия

#### Scenario: Просмотр закрытого пакета
- **WHEN** пользователь переходит в историю и открывает полностью проданный или погашенный пакет
- **THEN** его покупка, операции, выплаты и показатели доступны для просмотра и редактирования

### Requirement: Ранний просмотр покупок
Список и карточка сохранённых параметров MUST быть реализованы сразу после формы покупки, до выбора сохранённых банков и финансовых расчётов. После успешного сохранения покупки приложение MUST перенаправлять на её карточку с сообщением об успехе и переходом к списку.

#### Scenario: Результат сохранения доступен для проверки
- **WHEN** пользователь успешно сохраняет покупку
- **THEN** приложение открывает карточку этой покупки с сообщением об успехе и переходом к списку, где покупка доступна отдельной записью

### Requirement: Базовое оформление страниц MVP
Все страницы MVP MUST использовать согласованное оформление с общей навигацией, типографикой, отступами и оформленными кнопками, формами и таблицами. Основное действие MUST быть визуально заметным. Стили и JavaScript MUST загружаться локально, без внешних шрифтов, CDN и дополнительных сервисов.

#### Scenario: Единое оформление при переходах
- **WHEN** пользователь переходит между портфелем, формой покупки и карточкой пакета
- **THEN** страницы сохраняют общую навигацию, согласованные заголовки, отступы и стили элементов управления

### Requirement: Пустые состояния и обратная связь
Сообщения об успехе и ошибках MUST отличаться от обычного текста, а ошибки полей MUST располагаться рядом с соответствующими полями. Пустой список покупок MUST объяснять отсутствие данных и предлагать добавить покупку.

#### Scenario: Пустой портфель
- **WHEN** пользователь открывает главную страницу до добавления первой покупки
- **THEN** приложение показывает понятное пустое состояние с заметным действием «Добавить покупку»

#### Scenario: Ошибка и успешное сохранение формы
- **WHEN** пользователь сначала отправляет неверные данные, а затем исправляет их и сохраняет покупку
- **THEN** ошибки заметны рядом с соответствующими полями, введённые значения сохраняются, а после успешного сохранения карточка показывает заметное сообщение об успехе

### Requirement: Доступность на узком экране
На узком экране навигация, поля, редактор дат и кнопки MUST оставаться доступными. Широкие таблицы MUST не скрывать действия и могут прокручиваться в своём блоке.

#### Scenario: Работа на узком экране
- **WHEN** пользователь открывает список, карточку и форму покупки на узком экране
- **THEN** навигация и действия доступны, поля и строки дат помещаются по ширине, а широкие таблицы при необходимости прокручиваются внутри своего блока

### Requirement: Постоянное локальное хранение
Приложение MUST сохранять пакеты, банки, расписания, продажи и фактические выплаты в локальном хранилище и восстанавливать их после перезапуска. Первый запуск MUST создавать пустое хранилище без демонстрационных операций.

#### Scenario: Повторный запуск
- **WHEN** пользователь сохраняет пакет и подтверждает купон, завершает приложение и запускает его снова
- **THEN** пакет, банк, расписание и подтверждённый купон остаются доступными с прежними суммами и датами

### Requirement: Атомарные изменения и понятные ошибки
Приложение MUST сохранять связанные изменения целиком либо оставлять прежние данные. Ошибки проверки MUST объяснять причину и сохранять введённые значения в форме для исправления. Простое открытие страницы MUST не создавать и не удалять операции.

#### Scenario: Ошибка сохранения связанной истории
- **WHEN** сохранение покупки вместе с её расписанием не удаётся завершить
- **THEN** приложение не оставляет частично сохранённую покупку без расписания

#### Scenario: Исправление неверной формы
- **WHEN** пользователь отправляет продажу с количеством больше доступного остатка
- **THEN** приложение показывает причину отказа и оставляет введённые дату, цену и количество в форме
