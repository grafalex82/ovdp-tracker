# Архитектура базовой версии

## Context

См. `proposal.md` о назначении и согласованном scope. Реализованы каркас Flask/Jinja, схема SQLite версии 1, точные денежные значения и форма покупки; первый вариант списка и карточек задачи 2.2 ожидает подтверждения пользователя. Новое требование делает ISIN единственным идентификатором выпуска и переносит его реквизиты из покупок в общий источник. Новая структура получает номер 2; программа ещё не опубликована, все текущие данные разработки разрешено удалить, поэтому перенос старой базы не нужен. Приложение предназначено для одного пользователя на одном компьютере.

Документ нужен, поскольку новая модель данных связывает редактируемую историю, подтверждения выплат и несколько финансовых расчётов. Контракты поведения находятся в четырёх файлах `specs/*/spec.md` этого change.

## Goals / Non-Goals

**Goals:**

- Одна точка определения денежных потоков, остатков и себестоимости для всех экранов и обеих доходностей.
- Точное хранение денег и атомарное сохранение связанных изменений.
- Простая структура, в которой расчёты проверяются без запуска веб-сервера.
- Просмотр сохранённой покупки сразу после ввода и единое базовое оформление страниц MVP.
- Возможность позднее добавить загрузку данных по ISIN или расчёт сценария, не создавая для них инфраструктуру в MVP.

**Non-Goals:**

- Универсальный бухгалтерский движок, журнал неизменяемых событий, многоуровневая система репозиториев и отдельный REST API.
- Расчёт доходности относительно сегодняшней рыночной цены, моделирование реинвестирования купонов или прогноз ставок/курсов.
- Поддержка нескольких пользователей, процессов записи или сетевого развёртывания.

## Decisions

### 1. Flask/Jinja и несколько предметных модулей

Сервер формирует HTML на Jinja. Формы отправляются обычными запросами с перенаправлением после успешного сохранения; форма покупки закрывается и пользователь переходит в портфель с сообщением об успехе и обновлённой строкой ISIN. Ошибка оставляет пользователя в форме с введёнными значениями и защитой несохранённого ввода. JavaScript управляет строками купонных дат, значениями по умолчанию и подтверждением ухода с изменённой формы. Проверка и сохранение данных остаются серверными. Общий шаблон Jinja задаёт верхние вкладки и хлебные крошки; общие локальные CSS оформляют страницы без CDN и внешних шрифтов.

```text
Browser
   |
   v
Flask routes + Jinja templates
   |
   +--> Operations and validation --> Database --> sqlite3 --> Local DB
   |
   +--> Cash flows and analytics
```

При реализации достаточно Python-пакета приложения с модулями веб-маршрутов, доступа к БД, операций/проверок и расчётов, а также каталогов шаблонов, статических файлов и тестов. Отдельные классы сервисов для каждой сущности и интерфейсы под гипотетические хранилища не нужны.

Альтернативы: Qt потребовал бы другого интерфейса; SPA добавила бы frontend-сборку и отдельный API. Flask/Jinja выбран пользователем и покрывает формы и таблицы без этих затрат.

### 2. SQLite через стандартный sqlite3

Локальный файл базы размещается отдельно от исходников приложения, например в `instance/portfolio.sqlite3`, и не включается в Git. Класс `Database` владеет приватным соединением; внешние ключи включаются при его открытии. Для HTTP обёртка `with_database` из `ovdp_calculator/web.py` создаёт отдельный экземпляр на запрос, передаёт его первым аргументом обработчику и закрывает при завершении, включая исключения. При старте приложения отдельный временный экземпляр проверяет или создаёт схему и сразу закрывается. Связанные изменения покупки, расписания и подтверждений выполняются одной транзакцией. Проверка истории и запись выполняются в одной транзакции, чтобы не проверять устаревший остаток.

Вся структура SQLite, SQL, открытие/закрытие соединений и настройка хранилища сосредоточены в `ovdp_calculator/db.py`. Класс `Database` предоставляет высокоуровневые методы добавления и чтения банков, пакетов, плановых/фактических выплат и продаж, а также удаления пакета. Сам класс не зависит от Flask и не использует `g`, `current_app` или контекст приложения. Вне HTTP применяется `with Database(path) as database:`. Другие модули получают экземпляр явно, не выполняют SQL и не получают соединения, курсоры или `sqlite3.Row`: API возвращает обычные словари и списки, а ошибки ограничений выражает через `db.DataIntegrityError`.

Отдельная запись автоматически сохраняется одной транзакцией. Для связанных операций используется `with database.transaction():` без выдачи соединения; вызываемые внутри методы записи присоединяются к этой транзакции и не фиксируют её досрочно. Явное вложение таких контекстов запрещено. Метод `close()` допускает повторный вызов и откатывает незавершённые изменения; закрытый экземпляр не открывается повторно. Финансовые расчёты, преобразование денег и проверка хронологической согласованности выполняются в предметных модулях через этот API.

Основные тесты создают экземпляры `Database` без контекста Flask и используют только публичный API хранения. HTTP-тесты отдельно проверяют передачу экземпляра в обработчик, параметры маршрута и закрытие при успехе и ошибке. Узкие проверки неизвестной версии, незавершённой инициализации и жизненного цикла соединения выделяются в отдельный файл низкоуровневых тестов; только там допускается прямой SQLite для подготовки несовместимых файлов и проверки внутренних гарантий хранилища.

Достаточно следующих сущностей:

| Сущность | Основные данные и связь |
|---|---|
| Банк | Название для отображения и уникальный нормализованный ключ |
| Выпуск | Уникальный ISIN, одна валюта, номинал, купон на одну бумагу и дата погашения |
| Покупка | Ссылка на выпуск, дата покупки, цена одной бумаги, количество и банк |
| Плановая выплата выпуска | Выпуск, тип «купон/погашение», плановая дата, стабильный идентификатор |
| Фактическая выплата покупки | Уникальная пара «покупка + событие выпуска», фактическая дата и общая сумма |
| Продажа | Пакет, дата, цена одной бумаги, количество |

Суммы ожидаемых выплат вычисляются по общим плановым суммам выпуска и истории количества конкретной покупки. Для выпуска существует одно событие погашения, синхронизированное с его датой погашения; купонные даты уникальны внутри выпуска. В MVP один размер купона применяется ко всем купонным датам, а плановая сумма погашения одной бумаги равна номиналу. Дублировать эти реквизиты и календарь в каждой покупке не нужно. Подтверждение хранит общую сумму покупки и ссылается на её выпуск через общее событие; связь с событием другого выпуска отклоняется. Уникальность пары «покупка + событие» предотвращает повторное подтверждение, не объединяя поступления разных покупок.

Покупка хранит независимые дату, цену, исходное количество и банк и ссылается на выпуск. Позиция определяется только ISIN, валюта берётся из выпуска и служит фильтром отображения. Текущий остаток позиции равен сумме остатков покупок. Детали включают и действующие, и закрытые покупки; в переключателе закрытых позиций ISIN появляется при нулевом суммарном остатке.

Один ISIN всегда задаёт одну валюту, номинал, плановые суммы и общий календарь, включая сохранённые прошедшие даты. Нормализованная таблица выпусков с уникальным ISIN и ссылки покупок устраняют саму возможность разных реквизитов одной бумаги в разных покупках. Сохранение прежних независимых копий с проверкой только будущих дат отклонено: оно не выражает новый инвариант и допускает расхождения валюты или прошлого расписания.

При первой покупке нового ISIN общие реквизиты и покупка создаются атомарно; ошибка не оставляет новый выпуск или банк. Для известного ISIN форма показывает общие сведения без редактирования и вводит только параметры покупки. Переданный вопреки форме конфликтующий реквизит отклоняется, а не создаёт второй вариант выпуска. Явное исправление сведений выполняется на уровне облигации: проверяются истории всех её покупок, затем общее изменение и пересчёт ожиданий применяются целиком либо отклоняются. Фактические суммы и даты не перезаписываются.

Идентификаторы общих событий сохраняются при изменении дат; событие с фактической выплатой хотя бы одной покупки нельзя удалить через редактирование календаря. Полное удаление покупки удаляет её продажи и подтверждения, но сохраняет выпуск, общий календарь, банки и другие покупки. Выпуск без покупок не образует строку портфеля.

Альтернативы: PostgreSQL требует отдельного сервиса; ORM и инструмент миграций добавляют зависимости без необходимости на этом этапе. Используем обычный SQL и номер версии схемы. Маркер 2 позволяет отличить новую структуру от старой без реализации миграции. Несовместимая версия существующей базы приводит к понятной ошибке без автоматического удаления или изменения данных.

### 3. Точность, даты и распределение себестоимости

Ввод денег разбирается в `Decimal` из строки с точкой или запятой и максимум двумя знаками после разделителя. Лишние знаки, включая завершающие нули, отклоняются с ошибкой без автоматического округления. Допустимые исходные десятичные значения хранятся точно строками. Количество облигаций в покупке и продаже — целое положительное число; при умножении денежных значений до сотых на целое количество дробных копеек не возникает, и округление суммы операции не требуется. Агрегаты суммируют точные суммы операций. Денежные вычисления не выполняются через SQLite REAL или бинарные float. Для итерационного XIRR допустима отдельная численная арифметика после формирования точных денежных потоков.

Стоимость покупки — точное произведение цены и количества; выручка каждой продажи — такое же произведение. Себестоимость выбывающей части равна разности точных себестоимостей остатка до и после операции, что при цене до сотых эквивалентно цене покупки, умноженной на количество выбывших облигаций. Последнее выбытие списывает весь оставшийся баланс. Эти же части и их себестоимости используются в знаменателе простой годовой доходности.

Все даты — календарные, без времени суток, в хранении ISO `YYYY-MM-DD`. Текущая дата берётся локально на компьютере пользователя; для тестов используется фиксированная дата. Календарь выпуска может включать даты до конкретной покупки и не обрезается при её добавлении. Сроки доходности — фактическое число дней, делённое на 365, в том числе для високосных лет. Интервалы статистики включают обе границы. Календарные границы распределения погашений считаются прибавлением месяцев с переносом на последний день месяца при необходимости.

### 4. Один расчёт истории для остатков и выплат

История пакета просматривается хронологически. Проверяется целочисленность и положительность количества, допустимость сумм, дата продажи не ранее покупки и неотрицательность остатка на каждой операции. Погашение закрывает весь оставшийся после продаж пакет; продажи погашенных бумаг недопустимы. Изменение операции не должно создавать противоречие ни в одной последующей операции.

Внутри одного календарного дня принят порядок для расчёта прав на купон: покупка, купон, продажи, погашение. Продажи одного дня упорядочиваются стабильным идентификатором для воспроизводимого распределения округлённой себестоимости. Это техническое правило ручного трекера; отдельные даты фиксации владельцев не моделируются, а фактическую сумму купона пользователь может исправить при подтверждении.

Сохранённый на уровне выпуска купонный размер применяется ко всем его купонным датам. Отдельного поля ставки и расчёта накопленного купонного дохода нет: введённая цена — вся учитываемая стоимость одной бумаги. При купонной сумме 0 нулевые ожидания не требуют подтверждения и не участвуют в доходностях.

По умолчанию форма сохраняет совершённую, а не сценарную операцию: будущие даты покупки, продажи и фактической выплаты не принимаются. Прошедшие даты разрешены. Купонные даты общего календаря не позже погашения; ожидаемые выплаты конкретной покупки определяются только на датах от покупки до погашения с учётом её истории количества. До покупки количество равно нулю, поэтому прошлые события выпуска не создают ей поступлений или просроченных подтверждений.

### 5. Факт и прогноз — разные представления одной истории

Фактическая выплата замещает причитающееся ожидание конкретной покупки в полном наборе денежных потоков. Подтверждение хранит введённые дату и общую сумму, а не плановые реквизиты ISIN: фактические 795 вместо плановых 800 и другая дата получения допустимы. Редактирование общего календаря не меняет фактические поступления ни одной покупки; исправление факта выполняется явно через его форму.

Если срок выплаты прошёл без подтверждения, событие остаётся ожидаемым с меткой «Требует подтверждения». В прогнозе оно временно использует плановые дату и сумму. Показатели с такими потоками подписываются как предварительные. Это не признание денег полученными: в фактических итогах их нет. Купоны за период владения сохраняются даже после последующей продажи всех бумаг.

Пакет действующий, пока есть непроданный остаток без подтверждённого погашения. Прошедшая плановая дата сама по себе его не закрывает. Полностью проданный пакет исключается из ожидаемой доходности действующих вложений, даже если по нему ещё требуется подтвердить исторический купон; такое событие остаётся в истории выплат и месячной таблице.

### 6. Прибыль и две доходности

Определения, формулы и эталоны находятся в `specs/portfolio-analytics/spec.md`.

Полученная прибыль включает подтверждённые купоны и результат уже выбывших частей пакета; полная себестоимость непроданных бумаг из неё не вычитается. Ожидаемая прибыль охватывает весь срок пакета: фактические поступления плюс причитающийся прогноз минус покупка.

XIRR строится из отрицательного потока покупки и положительных потоков купонов, продаж и погашения. События одной даты суммируются, нулевые потоки отбрасываются. Для портфеля сначала выбираются действующие пакеты одной валюты и объединяются их полные потоки с исходных дат покупки. Это показатель этих вложений за весь срок, без отдельного денежного счёта и моделирования реинвестирования.

Численный модуль должен поддерживать отрицательную доходность и r > −1, ограничивать число итераций, проверять невязку и искать возможные альтернативные корни, а не безусловно доверять одному запуску Ньютона. Подход — поиск интервалов в преобразованной шкале `log(1+r)` и уточнение корней бисекцией; при отсутствии устойчивого решения или нескольких найденных корнях возвращается структурированная причина отсутствия показателя. Для сложных потоков нельзя обещать математическую уникальность результата только на основании успешной сходимости из одной точки. Корректность проверяется эталонами и случаем с двумя корнями.

Простая годовая доходность делит прибыль на сумму «себестоимость части × годы владения частью». Для проданных частей конец срока — дата продажи, для погашенных — фактическая дата, для ожидаемого остатка — плановая дата погашения. Даты купонов влияют на XIRR, но не на знаменатель простой доходности. На уровне портфеля складываются прибыли и знаменатели выбранных пакетов, а не их проценты.

Для позиции ISIN объединяются полные потоки только её действующих покупок в единой валюте выпуска: покупки с отрицательным знаком, подтверждённые выплаты, продажи и оставшиеся ожидания. Частично проданная покупка участвует со всей историей, полностью закрытая исключается из ожидаемого показателя позиции. События одной даты суммируются, начало расчёта — самая ранняя дата включённой покупки. Аналогично простая доходность позиции использует сумму прибылей и знаменателей. В портфеле показывается XIRR с подписью «Ожидаемая доходность, % годовых»; текущая рыночная цена не вводится, показатель не называется рыночной YTM. В деталях доступны обе метрики и их полный горизонт.

Аллокация реализуется отдельной задачей после расчёта текущей себестоимости: себестоимость остатка ISIN делится на себестоимость всех действующих остатков выбранной валюты. Закрытые части и другие валюты в знаменатель не входят. Расчёт выполняется из точных сумм, округляется только отображение процентов; нулевой знаменатель даёт отсутствие показателя, а не фиктивный процент. Сумма показанных долей может отличаться от 100% на величину округления.

Обе доходности показываются с двумя десятичными знаками. При нулевом сроке, пустых данных или невозможности расчёта отображается причина; 0% выводится только при действительно нулевой рассчитанной доходности. Фильтр периода применяется к операциям, но не меняет полный горизонт ожидаемой доходности. Для закрытого пакета доходность остаётся ожидаемой, если есть неподтверждённые причитающиеся события.

### 7. Иерархия экранов и поведение интерфейса

- Верхние вкладки: «Портфель» (главная), «Выплаты», «Статистика». Активный раздел выделяется на вложенных экранах. Рабочие экраны выплат и статистики подключаются в своих задачах; каркас навигации не подменяет реализацию их содержимого.
- Портфель: переключатель валюты UAH/USD/EUR фильтрует выпуски; действующие/закрытые позиции переключаются внутри портфеля. Одна строка на ISIN с текущим количеством, купоном на одну бумагу за одну выплату, оставшимися купонными датами, погашением, ожидаемой доходностью и аллокацией. Даты и цены покупок, банки и пакеты здесь не показываются. «Добавить облигацию» открывает форму покупки: известный ISIN использует общие реквизиты, новый требует их ввода. После сохранения возвращается портфель с сообщением об успехе.
- Детали облигации: общие реквизиты, номинал и себестоимость остатка, ближайшая выплата с датой и суммой, полученные купоны, ожидаемые поступления, полученная/ожидаемая прибыль и обе доходности. Ниже расположены расписание с плановыми/фактическими датами, суммами и статусами и таблица всех покупок с датой, банком, ценой, купленным количеством, стоимостью и остатком. По строке покупки открывается её карточка; продажи и исправления относятся к выбранной покупке.
- Карточка покупки: сохранённые параметры, её расписание, операции и показатели; отдельное подтверждение полного удаления. Покупка принадлежит деталям ISIN, даже если открыта по прямой ссылке или из другого раздела.
- Выплаты: ближайшие купоны и погашения, прошедшие неподтверждённые события и подтверждённая история с переходами к соответствующей покупке, выбор валюты и диапазона и месячная таблица. Группировка по ISIN/дате не объединяет подтверждения разных покупок в одну запись.
- Статистика: денежные операции за выбранный период, полученная/ожидаемая прибыль, доходности за полный срок и распределение текущих остатков по срокам погашения. Месячная таблица располагается во вкладке «Выплаты».

Хлебные крошки строятся по принадлежности данных, а не по истории переходов: «Портфель / ISIN», «Портфель / ISIN / Покупка №…», «Портфель / ISIN / Покупка №… / Редактирование». Исправление общего выпуска имеет путь «Портфель / ISIN / Редактирование облигации», добавление — «Портфель / Добавить облигацию». Предшествующие элементы являются ссылками, текущий — текстом. Все формы, включая общие реквизиты, используют одинаковую защиту несохранённых изменений.

Защита включается только при отличии введённых данных от сохранённых либо от исходного состояния новой формы. Уход по ссылке, вкладке или кнопке отмены предлагает «Остаться» и «Выйти без сохранения»; отмена ухода сохраняет весь ввод и страницу. Если пользователь вернул все исходные значения, предупреждение снимается. Для обновления, закрытия вкладки и внешней навигации применяется штатное предупреждение браузера в пределах его поддержки; произвольный текст для него не обещается. Подтверждённый уход не вызывает второе предупреждение. Успешная отправка формы и переход в портфель не требуют подтверждения; ошибка проверки или записи оставляет форму изменённой и защищённой, включая строки купонов.

Редактор календаря доступен при создании нового выпуска и его явном общем исправлении. Поля используют штатный элемент даты браузера с календарём и ручным вводом; известный ISIN в форме покупки показывает календарь без возможности его переопределить. Корректные даты сортируются после завершения ввода без потери незавершённых значений. Кнопка рядом со строкой удаляет только её; сервер проверяет уникальность и границу погашения, сохраняя ошибочные значения для исправления. Купон до даты отдельной покупки допустим в общем календаре. Перестановка строк не меняет идентификаторы событий; удалить событие с подтверждением любой покупки нельзя.

Только в черновике нового выпуска автоматическое погашение следует максимальной купонной дате до ручного изменения и очищается при удалении всех дат. Бескупонный выпуск требует ручного погашения. При повторной покупке это значение берётся из выпуска и не пересчитывается относительно даты покупки. Исправление существующего выпуска начинается с его сохранённой даты погашения и меняется явно, без автоматического сдвига из-за удаления строки календаря.

Базовый дизайн входит в MVP; страницы используют общие шаблоны и стили. Достаточно единого фона и контейнера содержимого, согласованных заголовков и размеров текста, отступов, оформленных кнопок, полей и таблиц. Основные действия визуально выделяются, ошибки располагаются у соответствующих полей, сообщение об успехе заметно после сохранения. Все элементы доступны на узком экране: верхние вкладки, хлебные крошки, формы и строки дат помещаются по ширине, а широкие таблицы при необходимости прокручиваются внутри своего блока. Отдельный UI-фреймворк и новые зависимости не требуются.

Начальный язык интерфейса — русский. Пресеты периода: текущий месяц, текущий квартал, текущий год, весь период и произвольный диапазон. Месячная таблица во вкладке «Выплаты» охватывает выбранный диапазон, включая пустые месяцы; её начальный диапазон — от текущего месяца до последнего ожидаемого погашения. Исторические даты доступны через фильтр. Графические библиотеки не подключаются.

### 8. Зависимости, запуск и проверки

Основная зависимость — Flask вместе со штатными Jinja/Werkzeug и прочими транзитивными пакетами. Версии совместимого набора фиксируются в файле зависимостей при реализации. Используется имеющийся Python 3.11; установка документируется через `python -m pip`, без виртуального окружения. Разработка не требует Docker, Node.js, отдельного frontend-toolchain или ORM.

Для автоматического тестирования используется pytest, зафиксированный вместе с зависимостями разработки в `requirements-dev.txt`. Он нужен для фикстур временных баз, параметризации и понятных отчётов об ошибках `assert`; приложение при обычном запуске его не использует. Установка средств разработки — `python -m pip install -r requirements-dev.txt`, запуск тестов — `python -m pytest`; конфигурация находится в `pytest.ini`.

Запуск — одна команда модуля приложения, привязка к `127.0.0.1`, debug и reloader по умолчанию выключены. В README нужно указать команду установки и запуска, расположение базы и порядок завершения. Локальный встроенный сервер применяется для данного личного инструмента; режим публичного сервера не проектируется.

Проверки выполняются pytest и тестовым клиентом Flask с временными SQLite-базами через фикстуру `tmp_path`. Тесты пишутся функциями с `assert`, фикстурами и параметризацией. Основные эталоны: XIRR 9,5445115% против простой доходности 10% за 730 дней; промежуточный купон; частичная продажа; объединение разных сроков; отрицательная доходность; несколько корней; перенос фактической даты; округления; отклонение несогласованного редактирования; каскадное удаление только выбранного пакета.

Проверки включают единый выпуск двух покупок, отказ от другого набора реквизитов того же ISIN, один календарь с разными правами на выплаты и отдельными фактическими поступлениями. Разные валюты тестируются разными ISIN; цена, дата покупки, банк и количество одного ISIN могут различаться. Низкоуровневые тесты проверяют пустое создание схемы 2, её связи и ограничения, сохранение данных после повторного запуска и отказ от несовместимой версии без перезаписи. Сквозные проверки покрывают общую правку с пересчётом всех покупок и сохранением факта, удаление одной покупки без удаления выпуска, крошки и защиту форм. Эталоны прибыли, доходностей и аллокации сохраняются; тесты переноса старой базы не нужны.

Источники технических решений: [Flask: установка и зависимости](https://flask.palletsprojects.com/en/stable/installation/), [sqlite3](https://docs.python.org/3/library/sqlite3.html), [Decimal](https://docs.python.org/3/library/decimal.html), [определение XIRR](https://support.microsoft.com/en-us/excel/functions/xirr-function).

## Risks / Trade-offs

- [Ошибки ручного расписания или суммы покупки] → Проверки формы и истории, возможность исправления и сохранение подтверждённых данных независимо от прогноза. API и банковская сверка не входят в MVP.
- [Совпадение купона и продажи в один день] → Явный воспроизводимый порядок расчёта и возможность указать фактическую сумму; рыночный механизм даты фиксации владельца пока не моделируется.
- [Просроченные неподтверждённые поступления и погашения] → Видимая отметка, предварительный статус прогноза и отсутствие сумм в фактической статистике.
- [Несколько корней или численная нестабильность XIRR] → Поиск альтернативных корней, контроль невязки, эталонные проверки и отсутствие произвольного процента при обнаруженной неоднозначности. Простая доходность и денежные суммы доступны независимо.
- [Расхождение округлённой себестоимости частей] → Распределение через разность остатков, проверка полного списания исходной стоимости.
- [Ошибочное редактирование истории] → Перепроверка всей хронологии и атомарная запись. Не вводится отдельный аудит всех версий.
- [Необратимое удаление или потеря локального файла] → Подтверждение полного удаления и документированное расположение базы. Автоматический бэкап и интерфейс восстановления в эту версию не включаются.
- [Общие зависимости Python без virtualenv] → Фиксация совместимых версий и документированный способ установки; ограничение принято пользователем.

## Migration Plan

Схема версии 2 создаёт общие выпуски и календари, покупки ссылаются на выпуск, подтверждения — на пару покупки и общего события. Повышение номера служит только маркером несовместимости; поддержка перехода с версии 1 не реализуется.

При реализации задачи 1.4 старый файл базы разработки однократно удаляется, после чего приложение создаёт пустую схему 2. Все нынешние данные разработки разрешено потерять; перенос покупок, событий и подтверждений, резервная копия ради миграции и разрешение старых конфликтов в этот этап не входят.

Обычный запуск не удаляет существующую базу автоматически. Совместимая версия 2 повторно открывается с сохранением записей; версия 1 или другая несовместимая версия отклоняется с объяснением необходимости отдельного пересоздания базы разработки. Такая проверка не заменяется простым присвоением нового номера старым таблицам.

Обновление артефактов не удаляет базу и не меняет код приложения; пересоздание выполняется в задаче реализации после проверок новой структуры на временных файлах.
