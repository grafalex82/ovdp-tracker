# local-web-app Specification

## Purpose

Предоставляет одному пользователю браузерный интерфейс учёта ОВДП с автозагрузкой параметров по ISIN и надёжно сохраняет историю на локальном компьютере между запусками.

## Requirements

### Requirement: Локальный запуск без отдельной инфраструктуры
Приложение MUST запускаться одной документированной командой Python после установки зависимостей и быть доступным в браузере только через loopback-интерфейс по умолчанию. Авторизация, Docker, virtualenv и внешняя СУБД MUST не требоваться. Доступ к API НБУ MUST требоваться только для автозагрузки по ISIN; запуск, просмотр и расчёты по сохранённым данным MUST работать без сети.

#### Scenario: Работа без сети
- **WHEN** зависимости установлены и пользователь запускает приложение на компьютере без доступа в интернет
- **THEN** приложение запускается без страницы входа, портфель, история и расчёты используют сохранённые данные без запросов к НБУ; попытка автозагрузки нового ISIN показывает сетевую ошибку с повтором или явным ручным вводом

### Requirement: Основные страницы
Приложение MUST предоставлять верхние вкладки «Портфель», «Выплаты» и «Статистика». Главная страница MUST открывать портфель. Внутри него MUST быть доступны детали выпуска ISIN, его покупки, отдельное исправление выпуска и покупки и переключатель действующих/закрытых позиций. Месячная таблица MUST располагаться во вкладке «Выплаты». Графики MUST отсутствовать в MVP.

#### Scenario: Работа с пакетом из портфеля
- **WHEN** пользователь выбирает ISIN в портфеле и затем покупку в деталях облигации
- **THEN** он последовательно видит сведения позиции и конкретной покупки, включая историю продаж, ожидаемые/полученные выплаты, прибыль, обе доходности и доступные действия

#### Scenario: Просмотр закрытого пакета
- **WHEN** пользователь выбирает закрытые позиции внутри портфеля и открывает облигацию и её полностью проданную или погашенную покупку
- **THEN** её параметры, операции, выплаты и показатели доступны для просмотра и редактирования; закрытая покупка ещё действующей позиции также доступна в деталях ISIN

### Requirement: Верхняя навигация
Верхние вкладки MUST сохраняться на вложенных экранах и выделять текущий раздел. Экран облигации, покупки и её редактирования MUST принадлежать портфелю независимо от пути открытия. Закрытые позиции MUST быть переключателем внутри портфеля, а «Добавить облигацию» MUST быть действием, а не отдельной верхней вкладкой.

#### Scenario: Переход между разделами
- **WHEN** пользователь переходит из портфеля в выплаты или статистику
- **THEN** меняется выделенная верхняя вкладка и содержимое соответствующего раздела, а общая структура навигации сохраняется

#### Scenario: Покупка открыта из выплат
- **WHEN** пользователь открывает конкретную покупку по ссылке из раздела выплат или напрямую
- **THEN** активной становится вкладка «Портфель», а положение покупки определяется её облигацией, а не предыдущей страницей браузера

### Requirement: Хлебные крошки
Вложенные страницы MUST показывать иерархию «Портфель / ISIN / Покупка / Действие» с необходимой глубиной. Каждый предшествующий элемент MUST быть ссылкой на соответствующего родителя, текущая страница MUST быть текстом. Новая покупка MUST иметь путь «Портфель / Добавить облигацию». Крошки MUST отражать принадлежность данных, а не историю посещений.

#### Scenario: Прямой переход к редактированию
- **WHEN** пользователь напрямую открывает редактирование покупки №3 облигации UA4000000001
- **THEN** показан путь «Портфель / UA4000000001 / Покупка №3 / Редактирование»; первые три элемента позволяют перейти на родительские страницы

#### Scenario: Детали облигации и добавление
- **WHEN** пользователь открывает ISIN из портфеля либо новую форму покупки
- **THEN** показан путь «Портфель / ISIN» либо «Портфель / Добавить облигацию» с кликабельным родителем и некликабельной текущей страницей

#### Scenario: Исправление общих реквизитов
- **WHEN** пользователь открывает исправление выпуска из деталей ISIN
- **THEN** показан путь «Портфель / ISIN / Редактирование облигации», а форма явно относится к общим реквизитам всех покупок этой бумаги

### Requirement: Разделение выпуска и покупки в формах
Ввод ISIN в режиме «НБУ» MUST запускать автозагрузку. Новый выпуск MUST получать общие поля, число купонов и пары дат/сумм автоматически, сохраняя параметры покупки. Известный ISIN MUST показывать сохранённые реквизиты и календарь без редактирования и перезаписи ответом API. При ошибке MUST быть доступны повтор и явный ручной ввод. Исправление общих реквизитов и сумм событий MUST быть отдельным действием на уровне облигации с защитой несохранённых изменений.

#### Scenario: Автозагрузка заполняет черновик
- **WHEN** пользователь вводит новый ISIN после указания даты, цены, количества и банка покупки, а НБУ возвращает выпуск и календарь
- **THEN** форма показывает успешную загрузку, общие параметры, вычисленное число купонов и пары дат/сумм; параметры покупки остаются введёнными, данные сохраняются только по действию «Сохранить»

#### Scenario: Загруженное погашение не следует правке купонов
- **WHEN** НБУ вернул погашение 2027-07-01 и последний купон 2027-06-01, а пользователь переключается в ручной режим, меняет свой календарь и возвращается в НБУ
- **THEN** нередактируемые данные НБУ сохраняют погашение 2027-07-01 независимо от ручного черновика

#### Scenario: Ошибка API сохраняет форму
- **WHEN** запрос НБУ не завершился успешно
- **THEN** форма показывает причину и действия повтора или ручного ввода, не стирает параметры покупки и не подставляет частичный календарь или фиктивные нули; для сохранённого ISIN остаются доступны его реквизиты

#### Scenario: Локальная работа без НБУ
- **WHEN** сеть недоступна и пользователь открывает сохранённый выпуск, его выплаты, статистику или добавляет повторную покупку
- **THEN** приложение использует сохранённые параметры и суммы событий без требования успешного ответа НБУ и без изменения истории

#### Scenario: Сохранённая валюта важнее значения по умолчанию
- **WHEN** пользователь выбирает существующий ISIN с валютой USD, хотя новая форма первоначально предлагала UAH
- **THEN** форма показывает USD и единые реквизиты выпуска без возможности задать для покупки UAH; сохранение добавляет только покупку и не создаёт второй выпуск

#### Scenario: Исправление покупки не меняет выпуск
- **WHEN** пользователь открывает исправление цены, даты, количества или банка покупки
- **THEN** форма не позволяет задать отдельные общие реквизиты ISIN, а переход к исправлению выпуска доступен как другое действие

### Requirement: Выбор режима добавления
Форма MUST иметь явный переключатель «НБУ / вручную» и отдельный блок даты, цены, количества и банка покупки. Режим НБУ MUST показывать реквизиты текстом и выплаты таблицей без редактирования. Ручной режим MUST запрашивать только номинал, валюту и купонные даты с суммами; при пустом списке MUST появляться дата погашения. Переключение MUST сохранять ручной черновик и параметры покупки. Ручной режим MUST не обращаться к НБУ.

#### Scenario: Нередактируемые данные НБУ
- **WHEN** загружены параметры нового ISIN из НБУ
- **THEN** реквизиты показаны текстом, выплаты таблицей с датами и суммами; пользователь вводит только параметры покупки

#### Scenario: Минимальный ручной ввод
- **WHEN** пользователь выбирает ручной режим и задаёт номинал, валюту и два купона с датами и суммами
- **THEN** другие общие поля не запрашиваются, погашение равно последней купонной дате и номиналу; пустой список купонов требует отдельной даты погашения

#### Scenario: Переключение не теряет ввод
- **WHEN** пользователь переключается с заполненного ручного режима в НБУ и обратно
- **THEN** ручные номинал, валюта и купоны, дата, цена, количество и банк покупки сохраняются; загруженные реквизиты НБУ остаются отдельным нередактируемым представлением

### Requirement: Подтверждение ухода с изменённой формы
Формы добавления и редактирования покупки и общего выпуска MUST предупреждать об уходе при несохранённых изменениях. Переход по вкладке, крошке, ссылке или кнопке отмены MUST предлагать «Остаться» и «Выйти без сохранения». Отказ MUST сохранять страницу и весь ввод без записи данных. Неизменённая форма или возврат всех исходных значений MUST не вызывать предупреждение.

#### Scenario: Отмена перехода по крошке
- **WHEN** пользователь меняет количество или купонные даты и нажимает родительскую крошку, а затем выбирает «Остаться»
- **THEN** переход не выполняется, все введённые поля и строки купонов остаются в форме, хранилище не меняется

#### Scenario: Подтверждённый уход
- **WHEN** пользователь с несохранёнными изменениями выбирает другую верхнюю вкладку и подтверждает выход без сохранения
- **THEN** открывается выбранный раздел без записи изменений и без второго предупреждения

#### Scenario: Все значения восстановлены
- **WHEN** пользователь изменяет форму, затем возвращает исходные значения всех полей и состава купонных дат и покидает страницу
- **THEN** переход выполняется без предупреждения

### Requirement: Защита формы при отправке и навигации браузера
При обновлении, закрытии страницы или уходе средствами браузера изменённая форма MUST запрашивать штатное подтверждение в пределах поддержки браузером. Успешное сохранение и переход в портфель MUST не требовать подтверждения ухода. Ошибка проверки или записи MUST сохранять введённые данные и защиту несохранённых изменений.

#### Scenario: Ошибка сохранения не снимает защиту
- **WHEN** изменённая форма возвращается с ошибкой проверки или записи и пользователь затем пытается уйти
- **THEN** все отправленные значения остаются доступны для исправления и уход требует подтверждения

#### Scenario: Успех и обновление страницы
- **WHEN** пользователь успешно сохраняет изменённую покупку
- **THEN** без предупреждения открывается портфель с сообщением об успехе; обновление портфеля не повторяет покупку

#### Scenario: Закрытие изменённой формы
- **WHEN** после изменения поля пользователь закрывает или обновляет страницу в браузере, поддерживающем подтверждение ухода
- **THEN** показывается штатное предупреждение браузера, а не обещанный приложением произвольный текст

### Requirement: Ранний просмотр покупок
Результат ввода MUST быть проверяем через портфель, детали облигации и карточку покупки. После успешного сохранения форма MUST закрываться, а приложение MUST перенаправлять в портфель с обновлённой позицией и сообщением об успехе. При ошибке пользователь MUST оставаться в заполненной форме.

#### Scenario: Результат сохранения доступен для проверки
- **WHEN** пользователь успешно сохраняет покупку
- **THEN** приложение закрывает форму покупки и открывает портфель с сообщением об успехе и обновлённым количеством позиции; через детали облигации доступна отдельная запись новой покупки

### Requirement: Базовое оформление страниц MVP
Все страницы MVP MUST использовать согласованное оформление с общей навигацией, типографикой, отступами и оформленными кнопками, формами и таблицами. Основное действие MUST быть визуально заметным. Стили и JavaScript MUST загружаться локально, без внешних шрифтов, CDN и дополнительных сервисов.

#### Scenario: Единое оформление при переходах
- **WHEN** пользователь переходит между портфелем, деталями облигации, формой, карточкой покупки, выплатами и статистикой
- **THEN** страницы сохраняют верхние вкладки, хлебные крошки на вложенных экранах, согласованные заголовки, отступы и стили элементов управления

### Requirement: Пустые состояния и обратная связь
Сообщения об успехе и ошибках MUST отличаться от обычного текста, а ошибки полей MUST располагаться рядом с соответствующими полями. Пустой портфель MUST объяснять отсутствие позиций и предлагать добавить облигацию. Недоступный финансовый показатель MUST показывать причину вместо фиктивного нуля.

#### Scenario: Пустой портфель
- **WHEN** пользователь открывает главную страницу до добавления первой покупки
- **THEN** приложение показывает понятное пустое состояние с заметным действием «Добавить облигацию»

#### Scenario: Ошибка и успешное сохранение формы
- **WHEN** пользователь сначала отправляет неверные данные, а затем исправляет их и сохраняет покупку
- **THEN** ошибки заметны рядом с соответствующими полями и форма сохраняет введённые значения; после успешного сохранения форма закрывается, а главная страница со списком показывает заметное сообщение об успехе

### Requirement: Доступность на узком экране
На узком экране навигация, поля, редактор дат и кнопки MUST оставаться доступными. Широкие таблицы MUST не скрывать действия и могут прокручиваться в своём блоке.

#### Scenario: Работа на узком экране
- **WHEN** пользователь открывает список, карточку и форму покупки на узком экране
- **THEN** навигация и действия доступны, поля и строки дат помещаются по ширине, а широкие таблицы при необходимости прокручиваются внутри своего блока

### Requirement: Постоянное локальное хранение
Приложение MUST сохранять единые выпуски ISIN, их календари, отдельные покупки, банки, продажи и подтверждения покупок и восстанавливать их после перезапуска. Первый запуск MUST создавать пустое хранилище без демонстрационных операций. Повторное открытие известного ISIN MUST использовать тот же выпуск независимо от банка или даты новой покупки.

#### Scenario: Повторный запуск
- **WHEN** пользователь сохраняет пакет и подтверждает купон, завершает приложение и запускает его снова
- **THEN** общий выпуск, календарь, покупка, банк и подтверждённый купон остаются доступны с прежними суммами и датами, без копии выпуска или календаря

### Requirement: Пересоздание базы разработки
После реализованной схемы 2 до публикации переход на структуру версии 3 с метаданными выпуска и суммой каждого события MUST выполняться однократным пересозданием базы разработки пустой. Перенос прежних данных MUST не требоваться. Обычный запуск MUST сохранять совместимую базу и отклонять несовместимую версию без автоматического удаления, перезаписи или присвоения нового номера старым таблицам. Обновление требований MUST не менять существующий файл базы.

#### Scenario: Пустая база новой структуры
- **WHEN** при переходе к новой структуре старый файл разработки удалён и приложение запускается без базы
- **THEN** создаётся пустая схема версии 3 с метаданными выпуска и отдельными суммами событий, без общего поля купона и переноса прежних покупок и подтверждений; последующее сохранение покупки и повторный запуск сохраняют новые данные

#### Scenario: Старый файл не удалён перед запуском
- **WHEN** приложение новой структуры открывает оставшийся файл версии 1, 2 либо другую несовместимую версию
- **THEN** запуск отклоняется с понятной причиной без изменения файла; приложение не удаляет данные и не запускает миграцию автоматически

### Requirement: Атомарные изменения и понятные ошибки
Приложение MUST сохранять связанные изменения целиком либо оставлять прежние данные. Ошибки проверки MUST объяснять причину и сохранять введённые значения в форме для исправления. Простое открытие страницы MUST не создавать и не удалять операции.

#### Scenario: Ошибка сохранения связанной истории
- **WHEN** сохранение первой покупки вместе с новым выпуском и его календарём не удаётся завершить
- **THEN** приложение не оставляет частичную покупку, новый выпуск, календарь или банк

#### Scenario: Исправление неверной формы
- **WHEN** пользователь отправляет продажу с количеством больше доступного остатка
- **THEN** приложение показывает причину отказа и оставляет введённые дату, цену и количество в форме
